## 0. House rules (read first)

1. **Local-first.** All changes go to local Docker first. Push to
   `origin/staging` (which auto-deploys to Railway) only after the
   user explicitly approves. The user's preference file
   `feedback_local_first.md` enforces this.
2. **No CHANGELOG / README / *.md** files unless explicitly asked.
3. **Migrations are forward-additive.** Down-migration SQL is hand-
   written alongside the up-migration when destructive (see
   `migrations/20260508100000_*/migration.down.sql` for the pattern).
   Prisma's `migrate` command does NOT auto-run *.down.sql.
4. **Hebrew UI.** The user works in mixed Hebrew/English. Many
   templates, phases, and zone names are in Hebrew. Sort order and
   label rendering must handle RTL gracefully.
5. **Stack**: NestJS (api) + React/Vite (web) + Prisma + MySQL,
   pnpm workspaces, Docker Compose for local, Railway for staging.

## 1. Project Planning grid (`apps/web/src/features/projects/planning-modal.tsx`)

The biggest surface in the app. Heavy iteration over 6 weeks.

### 1.1 Deliverable / Service model — finally aligned (10 May 2026)

**Conceptual model** (matches `/templates/deliverables` + `/templates/services`):

```
Service (= Phase)        — discipline / workstream
   └── Deliverable (= Template, type='task_list') — a named bundle of tasks
          └── Task                                 — concrete task in a project
```

**Schema:**
- `Phase` — Service catalog (id, name, color, sortOrder)
- `Template` — Deliverable catalog when `type='task_list'`. Has `phaseId` → parent Service.
- `Task` (project-side) carries:
  - `phaseId` → Service (Phase)
  - `deliverableTemplateId` → Deliverable (Template). **Added in migration `20260508100000_task_deliverable_template_id`.**
  - `serviceTypeId` → legacy ServiceType (kept as fallback for old data)
  - `description` may carry `[SERVICE:xxx]` markers (legacy)

**Read priority for Deliverable cell + bucketing**:
1. `task.deliverableTemplate?.name`  (new FK — source of truth)
2. `task.serviceType?.name`          (legacy ServiceType)
3. `[SERVICE:xxx]` description marker (legacy zone-template flow)
4. "No Deliverable" / "—"

**Phase is intentionally NOT in this chain** — it's a Service, not a
Deliverable. Including it made "Group by Deliverable" look identical
to "Group by Service".

**Write paths that set `deliverableTemplateId`** (all gated on
`template.type === 'task_list'`):
- `apps/api/src/modules/zones/zones.service.ts`
  - `applyTaskTemplate` — direct task-template apply
  - `applyProjectTemplate` — root, linkedTaskTemplate, referencedTemplate
  - `duplicateZone` — preserves source task's value
- Frontend `Add Deliverable at Project Root` dialog

**Data cleanup migration** (`20260510100000_cleanup_bad_deliverable_template_ids`)
NULLed out 79 tasks (locally) whose `deliverable_template_id`
incorrectly pointed at zone-templates. Idempotent. Will run
automatically on staging at first deploy after this is shipped.

### 1.2 Zone column shows the full breadcrumb
- `Building 1 › מרתף` instead of just `מרתף`.
- Critical when same leaf name exists under multiple parents.
- Computed server-side in `planning.service.ts` from `zone.path`.
- Column width: 180px in `TASK_GRID`.

### 1.3 Inline editing — Deliverable + Service cells
- Click any row's Deliverable / Service cell → dropdown opens.
- **Deliverable** sources from `/templates?type=task_list` — same
  list shown on `/templates/deliverables`.
- **Service** sources from `/phases` — full catalog (NOT project-scoped).
- `+ Create new…` POSTs a new entry and auto-selects it.
- Component: `CompactPickerCell` with `kind: 'deliverable' | 'phase'`.

### 1.4 Project Root section (tasks not tied to a zone)
- `tasks.zoneId` is nullable. Migration `20260507100000_task_zone_nullable`.
- **Add Task** + **Add Deliverable** buttons in the action bar.
- Renders as violet cards above the zone tree.
- Cards bucket by Deliverable (Template) primarily.

### 1.5 Drag & Drop
- **Tasks within zone**: `dnd-kit` sortable, persists to `Task.sortOrder`.
- **Tasks across zones**: same drag, **with confirm modal** ("Move task / Cancel").
- **Zone reorder**: persists to `Zone.sortOrder`. Works at every depth
  (only within the same parent's siblings).
- **Deliverable cards**: persist to `ServiceType.sortOrder` /
  `Phase.sortOrder` of the entity backing the card. Template-keyed
  cards are NOT draggable yet (Template has no `sortOrder` column).

### 1.6 Project-level totals strip (top of the planning view)
**Tasks · Budget hours · Logged hours · Budget amount · Progress %**
- Always visible above the action bar.
- Logged hours red when exceeding budget.

### 1.7 Per-task **Logged** column
- Sum of `TimeEntry.minutes` for the task. Aggregated server-side.
- Red bold when over budget.

### 1.8 Filters
- Status, Estimated start range, Due date range.
- **Has due date: Any / Yes / No** — for finding tasks missing schedule.

### 1.9 Group by — 4 modes
- **Zone** (default): hierarchical zone tree + Project Root cards.
- **Deliverable**: cards by `deliverableTemplate.name`.
- **Service**: cards by `phase.name`.
- **No Grouping**: single card with all tasks.

### 1.10 Collapse all / Expand all
- Toolbar button next to Group dropdown.
- Implemented via `BulkCollapseContext` + `useBulkCollapseSync` hook.
  Toggles a `version` counter so cards re-sync even when desired
  state hasn't changed (lets users mix manual + bulk toggles).

### 1.11 Bulk delete
- Floating action bar (when ≥1 row ticked) has a red **Delete** button.
- Styled confirm modal (NOT native browser confirm).
- Lists up to 5 names + "+N more".
- Row trash on a ticked row deletes the WHOLE selection
  (spreadsheet pattern matching the other bulk inline edits).

## 5. Task completion %

**Formula** (mirrors `apps/web/src/lib/task-health.ts` ↔ `time-entries.service.ts → syncTaskCompletion`):
| status | computedPct |
|---|---|
| `completed` | 100 |
| `cancelled` | 100 |
| `in_review` | 90 |
| anything else | `min(80, round(loggedHours / budgetHours × 80))` |

A task can never look "done" until status moves to Done. Workflow
contributes the last 20%. The two formulas (server persists,
client renders) MUST stay aligned — change them together.

Status flips also re-sync the persisted `Task.completionPct` even
when no time entry was logged (`tasks.service.update` →
`recomputeCompletionPct`).

`apps/web/src/features/templates/types-page.tsx`

|---|---|---|

| Project Categories | `/service-types` | Full CRUD |
| Departments | `/admin/config/departments` | Full CRUD |
| Professions | `/admin/config/professions` | Full CRUD |

**Zone Types** background: `ZoneType` is a Prisma enum (8 values:
`site, building, level, zone, area, section, wing, floor`). Adding
new types requires a migration. Editing label/color/icon/sortOrder
goes through the new `ZoneTypeMeta` table (1:1 with the enum).
Deletion removes the meta row only — the enum value stays valid
so existing zones keep working.

## 8. Live presence indicator (`apps/api/src/modules/presence/`)

- Banner at the top of each project page: "N people are viewing this project right now" + stacked avatars.
- HTTP polling architecture (NOT WebSocket):
  - `POST /presence/heartbeat` every 20s while mounted.
  - `POST /presence/leave` via `sendBeacon` on unmount.
  - `GET /presence/project/:id` polled every 10s.
  - In-memory `Map<projectId, Map<userId, lastSeenAt>>`. 60s TTL.
  - `@Cron` sweep every minute prunes stale entries.

## 9. Date formatting

- Canonical format **`DD-MMM-YYYY`** (e.g. `10-May-2026`).
- Helpers in `apps/web/src/lib/date-utils.ts`:
  - `formatDate` → `dd-MMM-yyyy`
  - `formatShortDate` → `dd-MMM`
  - `formatDateTime` → `dd-MMM-yyyy HH:mm`
  - `formatDuration(days)` → `Nd` / `Nmo` / `Ny Nmo` / `Ny`
- All inline `toLocaleDateString` calls in feature surfaces routed
  through these helpers.
